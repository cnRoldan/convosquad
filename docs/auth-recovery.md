# Auditoría y validación de autenticación

## Hallazgos y cambios

- Registro e inicio de sesión utilizan Supabase Auth con clave publicable, confirmación de correo, PKCE S256 y metadatos de usuario. No se cambian RLS, migraciones, permisos ni restricciones del servidor. `invalid_credentials` significa que Supabase rechazó el correo/contraseña; por sí solo no demuestra un fallo del callback. Ahora se muestra un mensaje específico sin revelar si una cuenta existe. La longitud mínima de ocho caracteres se exige al registrar o cambiar contraseña; el login permite comprobar contraseñas anteriores más cortas.
- El callback anterior aceptaba únicamente `code`. `exchangeCodeForSession` requiere el verificador almacenado donde se inició la solicitud; otro dispositivo, incógnito, otro perfil o dominio no lo comparte. Se mantiene PKCE, incluido `sb_flow_id`, y se explica cómo usar el código del correo cuando falta el verificador.
- La plantilla de recuperación pasa a `{{ .RedirectTo }}#token_hash={{ .TokenHash }}&amp;type=recovery`. La aplicación verifica con `verifyOtp({ token_hash, type: 'recovery' })` y exige una sesión devuelta por Supabase. Funciona sin trasladar el verificador PKCE. El fragmento evita que el hash viaje en la petición HTTP al alojamiento. Se requiere pulsar «Verificar enlace» antes de consumirlo, reduciendo la posibilidad de consumo por previsualizadores de correo. El hash y el código son secretos de un solo uso: no compartir capturas ni URLs completas.
- El callback admite también `signup` y `email` para plantillas de confirmación basadas en hash; esas verificaciones no activan recuperación. No acepta parámetros duplicados, credenciales mezcladas, sesiones implícitas ni tipos como `invite` o `email_change`. Un `type=recovery` junto a un código PKCE no concede modo recuperación: se usa el resultado del intercambio.
- Se leen enlaces iniciales y nuevos enlaces de Expo Linking; el acceso a `window` queda limitado a web. La hidratación estática no procesa credenciales hasta el cliente. Los códigos se intercambian una sola vez por instancia de callback y las credenciales se retiran del historial web tras intentarlo.
- Las sesiones web siguen en el almacenamiento que gestiona Supabase; React Native mantiene AsyncStorage, `processLock` y renovación al entrar en primer plano. El marcador de recuperación se conserva en AsyncStorage (localStorage en web), separado por proyecto y ligado al usuario y al instante de inicio de una sesión existente. Es un estado de navegación, no una autorización: Supabase continúa validando la sesión y los cambios. Se conserva si Supabase repite SIGNED_IN al recuperar el foco con la misma sesión y se limpia al iniciar una sesión nueva o cerrarla; no contiene tokens. La restauración espera al almacenamiento y descarta respuestas anteriores a eventos nuevos.
- Netlify conserva la exportación estática y el fallback de rutas. El callback recibe `Referrer-Policy: no-referrer` y `Cache-Control: no-store`.

## Configuración del proyecto alojado (pendiente de aplicar y probar)

El archivo local de plantilla **no actualiza** Supabase alojado. Esta PR no ejecuta operaciones administrativas ni envía correos. Después de revisar/desplegar el código, la persona responsable debe:

1. En Netlify configurar las variables públicas de Supabase durante la build, nunca claves secretas. Para web, dejar `EXPO_PUBLIC_AUTH_REDIRECT_URL` vacía para usar el origen abierto, o fijarla al callback HTTPS estable sin query ni fragmento. Una build móvil debe usar su callback `convosquad://auth/callback` autorizado, o una URL HTTPS deliberadamente elegida para recuperación en navegador. Expo Go usa su propia dirección de desarrollo; probar el esquema propio en una build instalada.
2. En Supabase configurar Site URL con el origen HTTPS y autorizar exactamente `https://DOMINIO/auth/callback` y los callbacks móviles usados. No usar un preview sin autorizarlo. El dominio del correo y el de la solicitud importan para PKCE; con hash no se necesita compartir almacenamiento.
3. En Authentication → Email Templates → Reset Password copiar el contenido de `supabase/templates/recovery.html`, conservando `.RedirectTo`, `.TokenHash` y `.Token`. Desactivar reescrituras/seguimiento de enlaces del proveedor SMTP si alteran o eliminan el fragmento. La aplicación siempre envía un redirect al solicitar recuperación; no añadir otra query o fragmento al callback configurado.
4. Mantener la plantilla Confirm signup actual con `.ConfirmationURL` si se desea PKCE. Confirmar desde otro navegador puede confirmar el correo pero impedir el intercambio; en ese caso iniciar sesión normalmente. Si se necesita también confirmación por hash entre dispositivos, una plantilla revisada puede usar `{{ .RedirectTo }}#token_hash={{ .TokenHash }}&amp;type=signup`. La aplicación lo admite, pero esta PR no cambia la plantilla remota de registro.
5. Verificar que `/auth/callback`, `/recover` y `/reset-password` sirven la aplicación al abrirlos directamente, y que las cabeceras del callback aparecen en Netlify. Enlaces enviados antes de actualizar la plantilla siguen siendo PKCE; solicitar un correo nuevo para probar hash.

## Prueba real que debe realizar el titular de la cuenta

Usar una cuenta de prueba propia ya existente. No usar usuarios ajenos. Cada escenario que consume un enlace/código necesita un correo nuevo; Supabase decide la caducidad, uso único y límites de envío.

1. **Chrome, mismo perfil:** abrir el sitio desplegado, solicitar recuperación y comprobar el mensaje que no revela la existencia de cuenta. Abrir el correo, pulsar «Verificar enlace» y comprobar que aparece Nueva contraseña. Recargar antes de guardar: debe continuar en recuperación. El titular puede guardar una contraseña diferente, volver al login e iniciar sesión. Cerrar sesión y recargar para comprobar su eliminación.
2. **Otro navegador/dispositivo:** solicitar desde Chrome y abrir el nuevo enlace en incógnito, Safari/Chrome móvil o un segundo equipo que nunca inició la solicitud. Debe verificar sin `code_verifier`, abrir Nueva contraseña y conservar el estado tras recarga. No compartir el enlace para hacer esta prueba: abrir el correo propio en el dispositivo elegido.
3. **Código manual:** solicitar otro correo; en otro navegador abrir Recuperar acceso, indicar el mismo correo y elegir «Tengo un código de recuperación». Introducir el código recibido. Debe abrir Nueva contraseña aunque no haya verificador local.
4. **App instalada:** solicitar desde la build móvil con el esquema autorizado; abrir el correo con la app cerrada y luego repetir con la app ya abierta. Comprobar ambas entregas del deep link, verificación, persistencia al reiniciar y renovación al volver de segundo plano. Abrir un callback HTTPS en móvil prueba la web, no la app nativa.
5. **Fallos:** reutilizar un enlace consumido y probar uno caducado; deben informar en español y ofrecer Recuperar acceso. Probar contraseña incorrecta, correo pendiente de confirmar y pérdida de conexión. Un enlace PKCE antiguo abierto en otro perfil debe explicar la necesidad del navegador original y ofrecer código/nuevo correo. Una ruta `/reset-password` sin sesión de recuperación debe llevar a Recuperar acceso.
6. **Registro/login:** el titular registra y confirma una cuenta de prueba si lo necesita, inicia sesión, recarga y cierra sesión. Confirmar tanto la ruta PKCE habitual como, si se configura, la variante por hash. No atribuir `invalid_credentials` a PKCE sin revisar el flujo que lo produjo.

Las pruebas automáticas usan almacenamiento aislado y fetch interceptado con el SDK real; no demuestran entrega SMTP, configuración del proyecto alojado, asociación del esquema móvil ni funcionamiento en producción. No afirmar corrección en producción hasta completar estos recorridos con correos reales.

## Verificación local de esta PR

El 14 de octubre de 2026 pasan `npm run check` (TypeScript y lint), `npm run test:unit` (43 pruebas, 18 nuevas de autenticación) y `npm run export:web` con configuración pública ficticia. Chromium, sobre esa exportación y con todas las peticiones a Supabase interceptadas, comprueba hash en un contexto nuevo sin almacenamiento compartido, botón de verificación, navegación a reset, recarga, error de caducidad, limpieza del historial, ausencia de verificador PKCE, parámetros duplicados, `invalid_credentials` y código OTP manual. No aparecen errores de navegador ni de hidratación. Las pruebas del SDK comprueban también PKCE en el navegador original, persistencia de sesión, eventos de recuperación y ausencia de sesión con token caducado. No se ha desplegado esta rama ni validado SMTP, Netlify público o builds móviles reales.
